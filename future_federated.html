🔭 Going Further: Federated Learning

Federated learning trains one shared model across many devices or organizations without collecting their raw data in one place. It is in real use, it is harder than it looks, and it reduces privacy risk rather than removing it.

📵 Data That Cannot Move

Every model in this course started with pd.read_csv: all the data in one table, on one machine. Often that is impossible or unwise. Text typed on millions of phones is too personal (and too large) to upload. Hospitals cannot pool patient records across institutions, and banks cannot share customer transactions with each other, even when a model trained on everyone's data would help everyone. Laws, contracts and plain common sense keep the data where it is.

Federated learning turns the usual direction around: instead of sending the data to the model, it sends the model to the data. Each participant, called a client (a phone, a hospital, a store), trains on its own data and sends back only the changes to the model. A central server combines those changes into a new shared model and sends it out again.

💡 Mental Model: The Recipe That Travels

Four Pinecrest stores each want a better trail-mix recipe, but no store may share its customer feedback. Head office mails the current recipe to every store. Each store tweaks it based on its own customers' comments and mails back only the tweaked recipe. Head office averages the tweaks, giving more weight to busier stores, and mails out the new version. After a few rounds every store has a recipe shaped by all customers, and no comment card ever left a store.

Two settings are common. Cross-device: millions of phones or browsers, each with a little data, many offline at any moment. Cross-silo: a handful of organizations, each with a large dataset and a reliable server.

🔁 Federated Averaging

The standard algorithm, federated averaging (FedAvg, from McMahan and colleagues, 2017), repeats one round many times:

graph TD A["Server: current global model"] --> B["Send model to clients"] B --> C["Each client trains locally"] C --> D["Clients send updated weights"] D --> E["Server: weighted average"] E -->|"next round"| A

The weight of each client in the average is its share of the data, nk / n. If every client took exactly one gradient step, FedAvg would be the same as gradient descent on the pooled data. Taking several local steps per round saves communication, which is the expensive part, at the cost of clients drifting apart when their data differs.

🧪 A Simulation on Pinecrest Stores

Pretend that each of Pinecrest's five channels (four stores and the online shop) keeps its own customer records and may not share them. The simulation below runs on one computer, but each client's rows are only ever touched inside that client's own function. Even the scaler respects the rule: clients share column sums, never rows, and the server computes the global mean and spread from them.

import numpy as np
import pandas as pd
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import roc_auc_score
from sklearn.model_selection import train_test_split

customers = pd.read_csv("data/customers_churn.csv")
features = ["tenure_months", "orders_12m", "spend_12m", "avg_order_value", "days_since_last_order",
            "returns_12m", "return_rate", "support_tickets_12m", "discount_share", "app_user"]
train, test = train_test_split(customers, test_size=0.25, stratify=customers["churned"], random_state=42)
clients = {store: (part[features].to_numpy(), part["churned"].to_numpy())
           for store, part in train.groupby("home_store")}
print({store: len(y) for store, (X, y) in clients.items()})

# global scaling from shared sums, never from rows
n = sum(len(y) for X, y in clients.values())
mean = sum(X.sum(axis=0) for X, y in clients.values()) / n
var = sum(((X - mean) ** 2).sum(axis=0) for X, y in clients.values()) / n


def scale(X):
    return (X - mean) / np.sqrt(var)


X_test, y_test = scale(test[features].to_numpy()), test["churned"].to_numpy()

Output

{'Asheville': 582, 'Bend': 611, 'Boise': 767, 'Flagstaff': 573, 'Online': 1967}

Each client runs a few steps of gradient descent for logistic regression on its own rows (the standard logistic-regression gradient: predicted probability minus label, times the features). The server averages the returned weights, weighted by client size:

def local_update(w, X, y, epochs=5, lr=0.5):
    """Runs on the client: a few gradient-descent steps on its own data only."""
    Xb = np.column_stack([np.ones(len(X)), scale(X)])
    for _ in range(epochs):
        p = 1 / (1 + np.exp(-Xb @ w))
        w = w - lr * Xb.T @ (p - y) / len(y)
    return w


w = np.zeros(len(features) + 1)                       # intercept + one weight per feature
X_test_b = np.column_stack([np.ones(len(X_test)), X_test])
for round_no in range(1, 31):
    updates = [(local_update(w, X, y), len(y)) for X, y in clients.values()]
    w = sum(w_k * n_k for w_k, n_k in updates) / n    # federated averaging
    if round_no in (1, 5, 10, 30):
        print(f"round {round_no:2d}  test AUC {roc_auc_score(y_test, X_test_b @ w):.3f}")

central = LogisticRegression().fit(scale(train[features].to_numpy()), train["churned"])
print(f"centralized logistic regression  test AUC {roc_auc_score(y_test, central.decision_function(X_test)):.3f}")
for store in ["Flagstaff", "Online"]:
    X, y = clients[store]
    alone = LogisticRegression().fit(scale(X), y)
    print(f"{store} alone  test AUC {roc_auc_score(y_test, alone.decision_function(X_test)):.3f}")

Output

round  1  test AUC 0.806
round  5  test AUC 0.821
round 10  test AUC 0.823
round 30  test AUC 0.824
centralized logistic regression  test AUC 0.823
Flagstaff alone  test AUC 0.815
Online alone  test AUC 0.818

After about ten rounds the federated model matches the model trained on pooled data, and no client ever revealed a row. Notice the last two lines too: here each channel has hundreds of customers who behave much like everyone else's, so even one store alone does almost as well. That is an honest result, and an important one: federation pays off when each client has too little data on its own, or sees only part of the picture, and when clients are similar enough that a shared model makes sense. Phones, each with a few hundred sentences, are the classic case.

🔐 Private Is Not Automatic

Keeping raw data on the device is a real improvement, but model updates are computed from that data and can leak it. Researchers have shown that, in some settings, training examples can be partly reconstructed from shared gradients, and that an attacker can test whether a particular record was used in training (a membership inference attack). Federated systems therefore add protections:

  • Secure aggregation: a cryptographic protocol that lets the server learn only the sum of many clients' updates, not any single client's update.
  • Differential privacy: each update is clipped and random noise is added, so that the final model provably depends very little on any one person's data. The guarantee is controlled by a privacy budget (epsilon), and stronger privacy costs accuracy, especially with few clients.
  • Data minimization: share only what training needs (as the scaler above shared sums, not rows), and keep logs and evaluation data local too.

⚠️ "Federated" Is Not a Privacy Guarantee

Treat "we use federated learning" as the start of a privacy conversation, not the end. Ask what is sent, who can see individual updates, whether differential privacy is applied and with what budget, and who controls the server.

🧗 What Makes It Hard

  • Data that differs between clients (called non-IID). A ski-town store and a desert store see different customers; local training pulls the shared model in different directions, and a single global model may serve some clients badly. Variants such as FedProx, and personalization (fine-tuning the global model locally), address this.
  • Unreliable clients. Phones go offline mid-round, so each round uses whichever subset of clients reports back, which can bias the model toward devices that are often charging on Wi-Fi.
  • Communication cost. Sending a large neural network to millions of devices is expensive; compression and fewer, longer local steps help.
  • Debugging without seeing data. You cannot inspect rows to find a labeling bug or a leak, and evaluation must also happen on the clients. Every habit from this course still applies; it is just harder to practice.
  • Malicious clients. A client can send poisoned updates to plant a backdoor. Robust aggregation rules help, at a cost.

⚖️ Where It Fits

Federated learning is past the research stage: it is used in production for tasks such as next-word prediction on phone keyboards, and in research collaborations between hospitals. Open-source frameworks, among them Flower, TensorFlow Federated and NVIDIA FLARE, handle the communication and orchestration. It remains more complex and slower to develop than ordinary training, so the honest test is simple: if the data can be pooled legally, safely and with consent, pooling it is easier and usually gives a better model. Reach for federated learning when it cannot be, and combine it with secure aggregation or differential privacy when the updates themselves are sensitive.

✅ Key Takeaways

  • Federated learning sends the model to the data: clients train locally and share only model updates
  • FedAvg averages client weights in proportion to their data; on the Pinecrest simulation it matches pooled training
  • It helps most when each client has too little data alone; with large, similar clients the gain can be small
  • Updates can leak information: secure aggregation and differential privacy are needed for real privacy guarantees
  • Different data per client, unreliable devices, communication cost and blind debugging make it harder than central training
