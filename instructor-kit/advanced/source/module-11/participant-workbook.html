Lessons

12.2

Serving and Monitoring Models

By the end you can
  • Package a fitted Pipeline with the metadata a server needs (features, dtypes, threshold, version)
  • Describe valid input with a pydantic model and read its validation errors
  • Serve predictions with FastAPI, test every endpoint with TestClient, and start the server with uvicorn
  • Measure input drift with the Population Stability Index and prediction drift with simple batch statistics
  • Tell a data-quality bug from a real change in customers, and say which one needs labels to confirm
Key ideas
  • The kitchen and the order window. FastAPI is the window, pydantic checks the order, the Pipeline is the kitchen. Bad orders get a 422 before the model runs.
  • Ship the facts the server cannot guess: the feature list, the training dtypes, the threshold, a version, and reference statistics from out-of-fold predictions.
  • One function rebuilds the training table: to_frame, with the same columns, order and dtypes as training. Prove it with a match test against the notebook, on rows with gaps.
  • NaN is not JSON: missing values travel as None (null).
  • TestClient tests endpoints in the same process; uvicorn serve:app --reload runs the real server, with interactive docs at /docs.
  • Monitoring without labels: PSI per input (below 0.1 stable, 0.1 to 0.25 watch, above 0.25 shift), missing rates and rejections, the mean score and offer rate against the reference.
  • Drift is a question: a data bug needs a fix (never retrain on it), a real change needs a decision, and only labels confirm the model got worse.
Worked example

A different request, the same window: store managers ask the demand model for next week's forecast. What does pydantic convert, and what does it refuse?

from datetime import date
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field, ValidationError
class StockRequest(BaseModel):
    """A store manager asks the demand model for next week's forecast."""
    model_config = ConfigDict(extra="forbid")
    store: Literal["Asheville", "Bend", "Boise", "Flagstaff"]
    product_id: str = Field(pattern=r"^[A-Z]{3}-\d{4}$")
    week_start: date
    promo: bool
r = StockRequest(store="Bend", product_id="SNW-2001", week_start="2025-12-01", promo="yes")
print(r.week_start.strftime("%A"), r.promo, type(r.week_start).__name__)
Monday True date

Lax mode turned the text date into a real date (a Monday) and the word "yes" into True. Now three bad requests:

for bad in [{"store": "Bend", "product_id": "snw-2001", "week_start": "2025-12-01", "promo": 1},
            {"store": "Bend", "product_id": "SNW-2001", "week_start": "2025-12-01", "promo": "maybe"},
            {"store": "Bend", "product_id": "SNW-2001", "week_start": "2025-13-01", "promo": 0, "units": 5}]:
    try:
        StockRequest(**bad)
    except ValidationError as err:
        print([(e["loc"][0], e["type"]) for e in err.errors()])
[('product_id', 'string_pattern_mismatch')]
[('promo', 'bool_parsing')]
[('week_start', 'date_from_datetime_parsing'), ('units', 'extra_forbidden')]

A lowercase product code fails the pattern, "maybe" is not a boolean, and a request with month 13 AND an unknown field reports both problems. Finally, strict mode: no conversions at all.

class StrictStockRequest(StockRequest):
    model_config = ConfigDict(extra="forbid", strict=True)
try:
    StrictStockRequest(store="Bend", product_id="SNW-2001", week_start="2025-12-01", promo="yes")
except ValidationError as err:
    print([(e["loc"][0], e["type"]) for e in err.errors()])
[('week_start', 'date_type'), ('promo', 'bool_type')]

Strict mode refuses text where a date or a boolean belongs. Lax is friendlier to callers that send everything as text; strict catches a caller that sends the wrong kind of value. Either way, write the choice down in the schema.

13.1

Case Study: Predicting Churn

By the end you can
  • Translate a business goal into a target, a metric and a dollar value for each kind of right and wrong prediction
  • Detect a target leak with cross-validation and a crosstab, and remove it before modeling
  • Compare and tune models inside a Pipeline with cross-validation, keeping the test set locked until one final check
  • Choose a decision threshold from business costs with TunedThresholdClassifierCV and report the result in dollars
  • Explain the model honestly and write a short recommendation for a non-technical stakeholder
Key ideas
  • The expedition plan: decision and costs first, then hazards (leaks), then comparison and tuning, the algorithm late.
  • Dollars define the rule: TP +$45, FP -$15. An offer pays when p > cost / value = 0.25, if the probabilities are calibrated.
  • Two baselines that matter to the manager: offer to nobody ($0) and to everyone (a loss). A model must beat $0.
  • Leak check: a sudden jump in score and a column filled only for one class are alarms; ask when each value becomes known.
  • Compare and tune with CV on the training data, same folds and metric; a gap smaller than the spread is noise. In a Pipeline: model__learning_rate.
  • Confirm the threshold on data with TunedThresholdClassifierCV and a profit scorer; then open the test set once.
  • Write for the reader: the decision, the dollars against the alternative, how sure you are, what the model does NOT explain, and an experiment to learn more.
Worked example

Eight customers, their predicted churn risk and (later) what happened. Each offer costs $15; reaching a would-be churner is worth $60. What is each offer worth before we know the outcome?

import numpy as np
import pandas as pd
toy = pd.DataFrame({"customer": list("ABCDEFGH"),
                    "p_churn": [0.82, 0.61, 0.44, 0.31, 0.27, 0.22, 0.12, 0.05],
                    "churned": [1, 1, 0, 1, 0, 0, 0, 0]})
OFFER_COST, CHURNER_VALUE = 15, 60
toy["expected_value"] = (toy["p_churn"] * CHURNER_VALUE - OFFER_COST).round(2)
print(toy.to_string(index=False))
customer  p_churn  churned  expected_value
       A     0.82        1            34.2
       B     0.61        1            21.6
       C     0.44        0            11.4
       D     0.31        1             3.6
       E     0.27        0             1.2
       F     0.22        0            -1.8
       G     0.12        0            -7.8
       H     0.05        0           -12.0

Expected value = p × 60 - 15: positive exactly when p is above 0.25. Now three thresholds, scored with the real outcomes:

def campaign_profit(y_true, flagged):
    y_true, flagged = np.asarray(y_true), np.asarray(flagged)
    return CHURNER_VALUE * ((flagged == 1) & (y_true == 1)).sum() - OFFER_COST * flagged.sum()
for t in [0.5, 0.25, 0.1]:
    flagged = (toy["p_churn"] >= t).astype(int)
    print(f"threshold {t:.2f}: {flagged.sum()} offers, profit ${campaign_profit(toy['churned'], flagged)}")
threshold 0.50: 2 offers, profit $90
threshold 0.25: 5 offers, profit $105
threshold 0.10: 7 offers, profit $75

The 0.25 line sends five offers and earns the most here: customer D (p = 0.31) churned and paid for two wasted offers. 0.5 leaves D out; 0.1 adds two customers whose expected value was negative. On eight customers luck plays a part; the case study confirms the same rule on 4,500.

Glossary

TermMeaning
servingLetting other software call a model, usually as a web API
endpointOne URL and method of an API, such as POST /predict
pydantic modelA Python class that describes and validates input
422FastAPI's status for a request that fails validation
TestClientSends requests to a FastAPI app in the same process, for tests
training-serving skewAny difference between how data was prepared for training and for serving
PSIPopulation Stability Index: how far a batch's distribution is from the reference
covariate shiftThe inputs change; the relationship may not
concept driftThe relationship between inputs and the target changes
break-even probabilitycost / value: above it an offer pays on average
TunedThresholdClassifierCVChooses a decision threshold by cross-validated score
model cardA short document that travels with a model: use, performance, limits
