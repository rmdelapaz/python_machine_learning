Session 4: Pipelines and Creating Features

How to teach Session 4 of Machine Learning Foundations: seal preprocessing and a model into one Pipeline that fits, cross-validates, tunes and saves as a unit (and watch a target-based feature fall from 0.930 to 0.586 once it is fitted inside the folds); then create features that let a linear model see thresholds, U-shapes, interactions, seasons and history (churn ROC AUC 0.829 → 0.883; demand error 11.3 → 9.4 units in class).

The #1 risk of Session 4: names and nesting swamp the idea

Lesson 2.2 is full of double-underscore names, nested branches and long error messages, and Lesson 2.3 is full of pandas. A room can spend the whole afternoon on syntax and leave without the two ideas that matter: every step that learns from data belongs inside the pipeline (0.930 vs 0.586 is the proof), and a linear model only sees straight lines unless you ask better questions (0.829 vs 0.883). Protect those two moments in the demos; when a name trips someone, show list(pipe.get_params()) once and move on. The labs repeat the naming until it sticks.

Answers
  1. W1 Precision (at 150): of the customers we contacted, how many were real churners? Recall would divide by all real churners instead.
  2. W2 0.667 0.667: two of the three flagged are churners (precision 2/3) and two of the three churners were flagged (recall 2/3).
  3. W3 The threshold is a setting learned from data. Choosing it on the test set lets the test set help build the model, so its score is no longer an honest preview. Out-of-fold probabilities give every training customer a score from a model that did not see them.
  4. W4 Reno is unknown, so with handle_unknown="ignore" it becomes a row of zeros; Boise is the second learned category. The category list was learned in fit.
  5. W5 The whole ColumnTransformer (imputer, scalers, ordinal and one-hot encoders), then the model, on the training folds only; then transform-and-predict on the validation fold. Doing that by hand is error-prone: a Pipeline does exactly this, which is today's first lesson.

Mental model to say

Say: "You could make espresso by hand: grind, weigh, tamp, heat, time the shot. Or you use a machine that does every step in order, the same way every time. Beans in, coffee out, and nobody can skip the grinder. A pipeline is that machine: transformers in order, one model at the end. It has fit and predict like any single model, so everything that works with a model (cross-validation, grid search, saving to a file) works with the whole machine. And it knows the one rule by heart: learn from training data, apply to everything else."

Then the stakes, pointing at the warm-up's W5 on the board: "In Session 3 you followed the rule by hand: fit_transform, then fit, then transform, then predict. Every rule you have to remember is a rule you will one day forget, at 6 p.m., in a cell you ran twice. From today, every model that needs preprocessing is a pipeline."

  5. The full churn pipeline (4m). "Lesson 2.1's preprocessor is itself a transformer, so it can be a step. Sixteen raw columns, text and gaps included, in; a probability out."

  8. The honest version (3m). "TargetEncoder computes the same kind of rate, but as a transformer: inside a pipeline it is refitted on the training folds of every round."

Three mistakes to expect, and how to coach each
  • A setting without its step name. ValueError: Invalid parameter 'C' for estimator Pipeline(steps=[('standardscaler', StandardS... Coach: "The pipeline has only four settings of its own; where does C live?" Then list(pipe.get_params()). The variant in the self-check (Q3): model__C on a make_pipeline pipeline, whose step is called logisticregression.
  • The model in the middle. TypeError: All intermediate steps should be transformers and implement fit and transform or be the string 'pas... (it also happens when a learner appends a scaler after the model to "scale the predictions"). Coach: "Which steps need a transform?" Transformers first, exactly one model last. Also expect ValueError: Estimator names must not contain __: got ['my__scaler'] when someone names a step my__scaler.
  • Believing the pipeline guards the columns too. A make_column_selector pointed at the whole table takes every text column, cancellation_reason included: CV ROC AUC 0.937, no error (the lesson's Common Mistake 5). Coach: "Which leak does a pipeline prevent: between rows, or from the future?" Rows only. The feature list is still the learner's job. A missing column at prediction time is the opposite case: ValueError: columns are missing: {'email_opens_90d'}, fixed by sending the column (empty if unknown).

Mental model to say

Say: "Think of a model as a very fast calculator with a fixed shape. Logistic regression can only add up weighted columns: more of a column always pushes the same way, by the same amount. It cannot say 'nothing much happens until 150 days, then risk jumps', and it cannot say 'tickets matter, but only without the app'. You are the interviewer who decides which questions the calculator gets. Ask 'days since the last order?' and it answers with a straight line. Also ask 'more than 150 days?' and it can express a jump."

Then the loop, on the board: explore the TRAINING rows → write a feature function → put it in the pipeline → cross-validate against the plain model → keep it or drop it. "Most ideas will not help. An idea that does not help is a cheap experiment, not a failure: you will record two of them today."

    def add_churn_features(df):
    df = df.copy()
    df["lapsed_150"] = (df["days_since_last_order"] > 150).astype(int)
    df["new_customer"] = (df["tenure_months"] < 6).astype(int)

  1. Name two things a Pipeline does that you had to remember by hand in Lesson 2.1, and one kind of leak it cannot prevent. Answer: it fits every step on the training rows and only transforms at prediction time; cross-validation and grid search refit every step inside each fold (and one file saves it all). It cannot stop a column from the future (cancellation_reason) that you put in the feature list.
  2. The signup-date churn rate scored 0.930 in cross-validation and 0.571 on the test set. Why, and what fixed the measurement? Answer: the rates were computed from every training label before the folds, so each validation row's own label was in its feature.
