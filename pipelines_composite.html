🔗 Lesson 2.2: Pipelines

Seal your preprocessing and your model into one object that fits, predicts, cross-validates, tunes and saves as a unit, so that test data can never leak into training by accident.

🧭 One Object, Every Step

At the end of Lesson 2.1 you had two fitted objects, a preprocess ColumnTransformer and a model, and a rule for using them: fit_transform then fit on training data, transform then predict on everything else, always in that order. You followed the rule. But every rule you have to remember is a rule you will one day forget, at 6 p.m., in a notebook cell you ran twice.

💡 Mental Model: The Coffee Machine

You could make espresso by hand: grind the beans, weigh them, tamp them, heat the water to the right temperature, time the shot. Or you could use a machine that does every step in order, the same way every time. You put beans in and get coffee out, and nobody can accidentally skip the grinder.

A pipeline is that machine for machine learning. Its steps are transformers, then one model at the end. It has the same fit and predict methods as any single estimator, so anything that works with a model (cross-validation, grid search, saving to a file) works with the whole machine. And the machine knows the one rule by heart: learn from training data, apply to everything else.

You have already met a tiny pipeline twice: in Lesson 1.3, make_pipeline(StandardScaler(), LogisticRegression()) kept the scaler inside the cross-validation folds, and in Lesson 2.1, make_pipeline chained an imputer and a scaler inside one branch. This lesson opens the object up and makes it your default. From here on, every model in this course that needs preprocessing is a pipeline.

Set up the same data and columns as Lesson 2.1's project:

import numpy as np
import pandas as pd
from sklearn.model_selection import train_test_split

pd.set_option("display.width", 150)

customers = pd.read_csv("data/customers_churn.csv")
complete = ["tenure_months", "orders_12m", "spend_12m", "avg_order_value", "days_since_last_order",
            "returns_12m", "return_rate", "support_tickets_12m", "discount_share", "app_user"]
nominal = ["home_store", "region", "age_group", "preferred_category"]
features = complete + ["email_opens_90d", "loyalty_tier"] + nominal

train, test = train_test_split(customers, test_size=0.25, stratify=customers["churned"], random_state=42)
X_train, y_train = train[features], train["churned"]
X_test, y_test = test[features], test["churned"]
print(X_train.shape, X_test.shape)

Output

(4500, 16) (1500, 16)

🧱 Building a Pipeline

Start small, with Lesson 1.1's model: the ten complete columns, a scaler and a logistic regression. make_pipeline takes the steps in order.

from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler

simple = make_pipeline(StandardScaler(), LogisticRegression())
simple.fit(X_train[complete], y_train)

print(simple)
print(f"test accuracy: {simple.score(X_test[complete], y_test):.3f}")

Output

Pipeline(steps=[('standardscaler', StandardScaler()),
                ('logisticregression', LogisticRegression())])
test accuracy: 0.848

The accuracy is 0.848, exactly Lesson 1.1's number, because the pipeline does exactly what you did by hand there. One fit call replaced three lines, and one score call replaced two. Here is what happens inside:

graph TD A["simple.fit(X_train, y_train)"] --> B["scaler: fit_transform"] B --> C["model: fit on scaled rows"] D["simple.predict(X_new)"] --> E["scaler: transform only"] E --> F["model: predict"]

During fit, every step except the last calls fit_transform and passes its output to the next step; the last step calls fit. During predict (and predict_proba, score), every step except the last calls transform only, using what it learned during fit, and the last step predicts. Nothing is ever refitted on the data you are predicting. That is the whole trick, and it is why the pipeline cannot leak.

Looking Inside

make_pipeline names each step after its class, in lowercase. You can reach a step by name, by position, or slice off the model to get the preprocessing part on its own:

print(list(simple.named_steps))
print("scaler means:", simple.named_steps["standardscaler"].mean_[:3].round(2))
print("model weights:", simple[-1].coef_.shape)
print("preprocessing only:", simple[:-1].transform(X_test[complete]).shape)

Output

['standardscaler', 'logisticregression']
scaler means: [ 41.48   5.   594.13]
model weights: (1, 10)
preprocessing only: (1500, 10)

simple[-1] is the fitted model and simple[:-1] is a pipeline of every step before it, which is handy when you want to see the data exactly as the model sees it.

Naming Your Own Steps

For bigger pipelines, choose the names yourself with the Pipeline class: a list of (name, step) pairs. Short, stable names such as "prep" and "model" make the rest of this lesson much easier to read, and they let you swap the model later without renaming anything.

from sklearn.pipeline import Pipeline

named = Pipeline([
    ("scale", StandardScaler()),
    ("model", LogisticRegression()),
])
named.fit(X_train[complete], y_train)
print(list(named.named_steps), round(named.score(X_test[complete], y_test), 3))

Output

['scale', 'model'] 0.848

🏗️ The Full Churn Pipeline

A ColumnTransformer is itself a transformer, so it can be a pipeline step. Put Lesson 2.1's preprocessor in front of the model and the whole churn workflow, from 16 raw columns to a probability, becomes one object.

from sklearn.compose import ColumnTransformer
from sklearn.impute import SimpleImputer
from sklearn.metrics import roc_auc_score
from sklearn.preprocessing import OneHotEncoder, OrdinalEncoder

preprocess = ColumnTransformer([
    ("scale", StandardScaler(), complete),
    ("email", make_pipeline(SimpleImputer(strategy="median", add_indicator=True), StandardScaler()),
     ["email_opens_90d"]),
    ("tier", make_pipeline(OrdinalEncoder(categories=[["Basic", "Silver", "Gold"]]), StandardScaler()),
     ["loyalty_tier"]),
    ("onehot", OneHotEncoder(sparse_output=False, handle_unknown="ignore"), nominal),
])

churn_pipe = Pipeline([
    ("prep", preprocess),
    ("model", LogisticRegression()),
])
churn_pipe.fit(X_train, y_train)

proba = churn_pipe.predict_proba(X_test)[:, 1]
print(f"test ROC AUC: {roc_auc_score(y_test, proba):.3f}")

Output

test ROC AUC: 0.828

The same 0.828 as Lesson 2.1, now from two lines of use instead of six. The pipeline takes raw rows: text, gaps and all. That matters most at prediction time, when a new customer arrives as a plain record:

one_customer = X_test.iloc[[0]]
print(one_customer[["days_since_last_order", "email_opens_90d", "home_store", "age_group"]])
print("churn probability:", churn_pipe.predict_proba(one_customer)[:, 1].round(3))

Output

      days_since_last_order  email_opens_90d home_store age_group
2111                     53              5.0  Asheville     25-34
churn probability: [0.061]

Note the double brackets in iloc[[0]]: they keep a one-row DataFrame, which is what the pipeline expects (a single bracket would give a Series, Lesson 1.1's mistake 2).

💡 See the Structure

In Jupyter, a pipeline displayed as the last line of a cell (without print) appears as an interactive diagram: click each box to see its settings. With print, as in this lesson, you get the same structure as text. Get used to looking at it: it is the quickest way to check that every column group goes where you meant.

🚰 Why Pipelines Stop Leaks

Lesson 1.3 showed two leaks: a scaler fitted before cross-validation (tiny), and features chosen from pure noise before cross-validation (huge). The rule behind both: any step that learns from data must be fitted inside each fold. Here is a leak you could easily write on real data, with no noise columns involved.

Customers joined on 2,150 different dates. Someone suggests a clever feature: for each signup date, the churn rate of customers who joined that day. It is a kind of target encoding (replacing a category with the average target for that category), a technique you met in Lesson 2.1's Common Questions. Computed with pandas on the training rows, then cross-validated:

from sklearn.model_selection import StratifiedKFold, cross_val_score

cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=42)

date_rate = y_train.groupby(train["signup_date"]).mean()
X_date = pd.DataFrame({"signup_churn_rate": train["signup_date"].map(date_rate)})

leaky = cross_val_score(LogisticRegression(), X_date, y_train, cv=cv, scoring="roc_auc")
print(f"leaky CV ROC AUC: {leaky.mean():.3f}")

Output (no error, and that is the problem)

leaky CV ROC AUC: 0.930

An AUC above 0.9 from the signup date alone, better than the full 16-column model. Too good to be true, and it is not true. Most dates have only one or two customers, so "the churn rate on your signup date" is mostly your own churn label. The rates were computed with every training row, including the rows that later sit in each validation fold, so the model was handed the answers. Now do it properly: scikit-learn's TargetEncoder computes the same kind of rate, but as a transformer, so a pipeline refits it on the training folds of every round.

from sklearn.preprocessing import TargetEncoder

honest_pipe = make_pipeline(TargetEncoder(cv=cv), LogisticRegression())
honest = cross_val_score(honest_pipe, train[["signup_date"]], y_train, cv=cv, scoring="roc_auc")
print(f"honest CV ROC AUC: {honest.mean():.3f}")

honest_pipe.fit(train[["signup_date"]], y_train)
test_auc = roc_auc_score(y_test, honest_pipe.predict_proba(test[["signup_date"]])[:, 1])
print(f"test ROC AUC     : {test_auc:.3f}")

Output

honest CV ROC AUC: 0.586
test ROC AUC     : 0.571

The honest cross-validation score and the test score agree: the signup date carries a little real signal (it encodes tenure, which you already have) and nothing like 0.9. The leaky number was not a better model; it was a broken measurement. Inside a pipeline, the encoder is refitted on four folds and applied to the fifth, every round, so the validation rows never shape the rates they are scored with. (TargetEncoder also uses its own internal folds during fit_transform, which is what the cv= argument controls, so even the training rows do not see their own label.)

⚠️ Steps That Learn from the Target Leak the Most

A leaky scaler costs you a few thousandths of AUC. Leaky steps that look at y (target encoding, feature selection, resampling for imbalanced classes in Lesson 2.5) can turn a useless model into a "great" one. You do not need to judge each case: put every learning step in the pipeline and the question disappears.

Cross-Validating the Whole Pipeline

Because the full churn pipeline is a single estimator, cross-validating it is one call, and every fold refits the imputer, the scalers, the encoders and the model from scratch on that round's training folds. Compare it with a baseline pipeline:

from sklearn.dummy import DummyClassifier

baseline_pipe = Pipeline([("prep", preprocess), ("model", DummyClassifier(strategy="prior"))])

for name, pipe in [("baseline", baseline_pipe), ("logistic regression", churn_pipe)]:
    scores = cross_val_score(pipe, X_train, y_train, cv=cv, scoring="roc_auc")
    print(f"{name:20s} CV ROC AUC {scores.mean():.3f} +/- {scores.std():.3f}")

Output

baseline             CV ROC AUC 0.500 +/- 0.000
logistic regression  CV ROC AUC 0.833 +/- 0.021

cross_val_score clones the pipeline for each fold, so your fitted churn_pipe is untouched. Notice what you did not have to do: no manual refitting of five transformers inside a loop. The test set stayed locked away the whole time.

🎛️ Settings, Swaps and a First Grid Search

Every setting of every step is reachable from the top of the pipeline, through names joined by a double underscore: step__parameter, and deeper, step__substep__parameter. List a few:

params = churn_pipe.get_params()
for key in ["model__C", "model__max_iter", "prep__email__simpleimputer__strategy", "prep__onehot__handle_unknown"]:
    print(f"{key:40s} {params[key]!r}")
print(len(params), "settings in total")

Output

model__C                                 1.0
model__max_iter                          100
prep__email__simpleimputer__strategy     'median'
prep__onehot__handle_unknown             'ignore'
73 settings in total

Read prep__email__simpleimputer__strategy from left to right: the step named prep, its branch named email, that branch's step named simpleimputer (the automatic make_pipeline name), and its strategy setting. set_params uses the same names. Lower C means stronger regularization (Lesson 3.2 explains it); here it is just a knob to turn:

for c_value in [0.01, 1.0]:
    churn_pipe.set_params(model__C=c_value)
    scores = cross_val_score(churn_pipe, X_train, y_train, cv=cv, scoring="roc_auc")
    print(f"C={c_value:<5} CV ROC AUC {scores.mean():.3f}")

Output

C=0.01  CV ROC AUC 0.835
C=1.0   CV ROC AUC 0.833

The loop ends with C=1.0, the default, so churn_pipe is back where it started.

Swapping a Whole Step

A step name can also be given a whole new object. Swap the logistic regression for a gradient-boosting model (Lesson 5.3 explains how it works; Lesson 1.1 showed that you do not need to know yet to use it):

from sklearn.base import clone
from sklearn.ensemble import HistGradientBoostingClassifier

boost_pipe = clone(churn_pipe).set_params(model=HistGradientBoostingClassifier(random_state=42))
scores = cross_val_score(boost_pipe, X_train, y_train, cv=cv, scoring="roc_auc")
print(f"gradient boosting CV ROC AUC {scores.mean():.3f} +/- {scores.std():.3f}")

Output

gradient boosting CV ROC AUC 0.861 +/- 0.013

clone makes an unfitted copy with the same settings, so churn_pipe keeps its logistic regression. Boosting beats logistic regression by about 0.03 AUC on the same preprocessing, which suggests the real churn patterns are not a simple weighted sum. Module 5 investigates. (Boosting does not need the scalers, but they do it no harm.)

A First Grid Search

Trying settings in a loop by hand gets tedious. GridSearchCV tries every combination in a grid, cross-validates each one, and refits the best on all the training data. It is itself an estimator, and because it receives the whole pipeline, every combination is evaluated without leaks. Lesson 6.2 covers tuning properly; here is the shape of it:

from sklearn.model_selection import GridSearchCV

grid = GridSearchCV(
    churn_pipe,
    param_grid={
        "model__C": [0.01, 0.1, 1.0],
        "prep__email__simpleimputer__strategy": ["median", "mean"],
    },
    cv=cv, scoring="roc_auc",
)
grid.fit(X_train, y_train)
print(grid.best_params_)
print(f"best CV ROC AUC {grid.best_score_:.3f}")

Output

{'model__C': 0.01, 'prep__email__simpleimputer__strategy': 'median'}
best CV ROC AUC 0.835

Six combinations times five folds is 30 fits plus one final refit, all in a few lines. Look at how little the choices matter: the fill strategy and a hundredfold change in C move the score only in the third decimal. Knowing that something does not matter is a useful result too, and you could only learn it cheaply because the pipeline made every variant one line.

🧪 Custom Steps with FunctionTransformer

Lesson 2.1 showed that a log transform changes the shape of skewed columns such as days_since_last_order. A plain function like np.log1p is not a transformer, but FunctionTransformer turns it into one, so it can live in a pipeline. It learns nothing during fit; it just applies the function. feature_names_out="one-to-one" tells it that the output columns keep the input names.

from sklearn.preprocessing import FunctionTransformer

skewed = ["spend_12m", "avg_order_value", "days_since_last_order"]
others = [c for c in complete if c not in skewed]

log_prep = ColumnTransformer([
    ("log", make_pipeline(FunctionTransformer(np.log1p, feature_names_out="one-to-one"), StandardScaler()), skewed),
    ("scale", StandardScaler(), others),
    ("email", make_pipeline(SimpleImputer(strategy="median", add_indicator=True), StandardScaler()),
     ["email_opens_90d"]),
    ("tier", make_pipeline(OrdinalEncoder(categories=[["Basic", "Silver", "Gold"]]), StandardScaler()),
     ["loyalty_tier"]),
    ("onehot", OneHotEncoder(sparse_output=False, handle_unknown="ignore"), nominal),
])
log_pipe = Pipeline([("prep", log_prep), ("model", LogisticRegression())])

scores = cross_val_score(log_pipe, X_train, y_train, cv=cv, scoring="roc_auc")
print(f"with log1p on 3 skewed columns: CV ROC AUC {scores.mean():.3f}")
print(log_pipe.fit(X_train, y_train)[:-1].get_feature_names_out()[:4])

Output

with log1p on 3 skewed columns: CV ROC AUC 0.812
['log__spend_12m' 'log__avg_order_value' 'log__days_since_last_order'
 'scale__tenure_months']

Worse, not better: 0.812 against 0.833 without the log. The histograms in Lesson 2.1 looked nicer after the log, but the model does not care about pretty histograms. Churn jumps sharply once a customer goes about 150 days without ordering, and the log squeezes exactly that region (150 and 300 days end up close together), so a straight line in log units fits the jump worse. The lesson is the method, not the transform: because the log was a pipeline step, testing it honestly took one cross-validation call, and the evidence says leave it out. Lesson 2.3 builds features that capture such thresholds directly.

💡 Stateless or Learning?

FunctionTransformer with a fixed function like np.log1p is stateless: it learns nothing, so it cannot leak even outside a pipeline. A step that computes anything from the data (a mean, a list of categories, a churn rate) is stateful and must be fitted inside the folds. When in doubt, put it in the pipeline; it costs nothing.

💾 Saving a Fitted Pipeline

The fitted pipeline holds everything needed to score a new customer: the fill values, the means, the category lists and the model weights. Save it as one file with joblib (installed with scikit-learn), load it in another program, and it predicts on raw rows straight away.

import joblib

joblib.dump(churn_pipe, "churn_pipeline.joblib")
loaded = joblib.load("churn_pipeline.joblib")

same = np.allclose(loaded.predict_proba(X_test)[:, 1], churn_pipe.predict_proba(X_test)[:, 1])
print("identical predictions after reloading:", same)

Output

identical predictions after reloading: True

🛑 Only Load Files You Trust

A joblib (or pickle) file can contain instructions that run when it is loaded. Loading a model file from an unknown source is as risky as running an unknown program. Only load files you or your team created. Lesson 12.1 shows the safer skops format and how to record which library versions a model needs, because a file saved with one scikit-learn version is not guaranteed to load in another.

⚠️ Common Mistakes

Pipeline errors are mostly about names and order. The messages are long, but the important part is always near the start.

1. Setting a Parameter Without Its Step Name

make_pipeline(StandardScaler(), LogisticRegression()).set_params(C=0.1)

Error

ValueError: Invalid parameter 'C' for estimator Pipeline(steps=[('standardscaler', StandardScaler()),
                ('logisticregression', LogisticRegression())]). Valid parameters are: ['memory', 'steps', 'transform_input', 'verbose'].

What it means: the pipeline itself has no setting called C; its own settings are only the four listed. Fix: prefix the step name, set_params(logisticregression__C=0.1) (or model__C with your own names). If unsure of the names, print list(pipe.get_params()). The same names go into a GridSearchCV grid.

2. Putting the Model Before a Transformer

backwards = Pipeline([("model", LogisticRegression()), ("scale", StandardScaler())])
backwards.fit(X_train[complete], y_train)

Error

TypeError: All intermediate steps should be transformers and implement fit and transform or be the string 'passthrough' 'LogisticRegression()' (type <class 'sklearn.linear_model._logistic.LogisticRegression'>) doesn't

What it means: every step except the last must have transform, because its output feeds the next step. A model has predict, not transform. Fix: transformers first, exactly one model last.

3. A Column Missing at Prediction Time

churn_pipe.predict_proba(X_test.drop(columns="email_opens_90d"))

Error

ValueError: columns are missing: {'email_opens_90d'}

What it means: the ColumnTransformer selects columns by name, and a column it was fitted with is absent. This is common when a production system sends a slightly different record. Fix: send every column the pipeline was trained on (churn_pipe.feature_names_in_ lists them); a column that is unknown for a customer should be present and empty (NaN), which the imputer handles.

4. Double Underscores in a Step Name

Pipeline([("my__scaler", StandardScaler()), ("model", LogisticRegression())]).fit(X_train[complete], y_train)

Error

ValueError: Estimator names must not contain __: got ['my__scaler']

What it means: __ is the separator in step__parameter, so it cannot appear inside a name. Fix: use single underscores or plain words, such as "my_scaler".

5. Selecting Columns by Type and Grabbing the Leak

Listing columns by hand is tedious, and make_column_selector can pick them by dtype instead. It is a fine tool, but watch what happens when it is pointed at the whole customer table:

from sklearn.compose import make_column_selector

everything = customers.drop(columns="churned")
auto_prep = ColumnTransformer([
    ("nums", make_pipeline(SimpleImputer(strategy="median"), StandardScaler()), make_column_selector(dtype_include="number")),
    ("text", make_pipeline(SimpleImputer(strategy="constant", fill_value="none"), OneHotEncoder(handle_unknown="ignore")),
     make_column_selector(dtype_exclude="number")),
])
auto_pipe = make_pipeline(auto_prep, LogisticRegression(max_iter=1000))

print(make_column_selector(dtype_exclude="number")(everything))
scores = cross_val_score(auto_pipe, everything.loc[X_train.index], y_train, cv=cv, scoring="roc_auc")
print(f"CV ROC AUC {scores.mean():.3f}")

Output (no error, and that is the problem)

['customer_id', 'signup_date', 'home_store', 'region', 'age_group', 'loyalty_tier', 'preferred_category', 'cancellation_reason']
CV ROC AUC 0.937

What happened: the selector took every text column, including cancellation_reason, the leak from Lesson 1.2, plus customer_id and signup_date one-hot encoded into thousands of useless columns. The score jumped well above the honest 0.83, and the pipeline did nothing wrong: it faithfully used the columns you gave it. A pipeline prevents leaks between rows (training versus validation); it cannot know that a column is from the future. Fix: list your feature columns explicitly, as this course does, or drop the ID, date and leak columns before using a selector.

🛠️ Project: A Deployable Churn Pipeline

Pinecrest wants a churn model that the IT team can run every month on fresh customer records without calling you. That means one file that takes raw rows and returns probabilities, chosen by an honest comparison and tested once. Build it in a new notebook called lesson_2_2_project. Allow about 40 minutes.

🛠️ Step 1: Load, split and define the columns (5 min)

import joblib
import numpy as np
import pandas as pd
from sklearn.compose import ColumnTransformer
from sklearn.dummy import DummyClassifier
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.impute import SimpleImputer
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import roc_auc_score
from sklearn.model_selection import StratifiedKFold, cross_val_score, train_test_split
from sklearn.pipeline import Pipeline, make_pipeline
from sklearn.preprocessing import OneHotEncoder, OrdinalEncoder, StandardScaler

customers = pd.read_csv("data/customers_churn.csv")
complete = ["tenure_months", "orders_12m", "spend_12m", "avg_order_value", "days_since_last_order",
            "returns_12m", "return_rate", "support_tickets_12m", "discount_share", "app_user"]
nominal = ["home_store", "region", "age_group", "preferred_category"]
features = complete + ["email_opens_90d", "loyalty_tier"] + nominal

train, test = train_test_split(customers, test_size=0.25, stratify=customers["churned"], random_state=42)
X_train, y_train = train[features], train["churned"]
X_test, y_test = test[features], test["churned"]
cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=42)
print(X_train.shape, X_test.shape)

Output

(4500, 16) (1500, 16)

🛠️ Step 2: Build the pipeline (10 min)

Write the preprocessor once, then a small function that puts any model behind it, so every candidate gets identical preparation.

preprocess = ColumnTransformer([
    ("scale", StandardScaler(), complete),
    ("email", make_pipeline(SimpleImputer(strategy="median", add_indicator=True), StandardScaler()),
     ["email_opens_90d"]),
    ("tier", make_pipeline(OrdinalEncoder(categories=[["Basic", "Silver", "Gold"]]), StandardScaler()),
     ["loyalty_tier"]),
    ("onehot", OneHotEncoder(sparse_output=False, handle_unknown="ignore"), nominal),
])

def churn_pipeline(model):
    return Pipeline([("prep", preprocess), ("model", model)])

candidates = {
    "baseline": churn_pipeline(DummyClassifier(strategy="prior")),
    "logistic regression": churn_pipeline(LogisticRegression()),
    "gradient boosting": churn_pipeline(HistGradientBoostingClassifier(random_state=42)),
}
print(list(candidates))

Output

['baseline', 'logistic regression', 'gradient boosting']

All three pipelines share one preprocess object. That is safe here: cross_val_score fits clones, and the project fits only the winner. But if you fit two of these pipelines yourself, they share one fitted preprocessor and the last fit silently wins (Lesson 2.5 meets this trap). When you want separate fitted copies side by side, give each pipeline its own clone(preprocess).

🛠️ Step 3: Compare by cross-validation (10 min)

Same folds for every candidate, training rows only.

cv_auc = {}
for name, pipe in candidates.items():
    scores = cross_val_score(pipe, X_train, y_train, cv=cv, scoring="roc_auc")
    cv_auc[name] = scores.mean()
    print(f"{name:20s} CV ROC AUC {scores.mean():.3f} +/- {scores.std():.3f}")

best_name = max(cv_auc, key=cv_auc.get)
print("chosen:", best_name)

🏋️ Exercise 3: A Pipeline for Demand, with a Log Target

Pipelines work for regression too. In data/weekly_demand.csv, train on 2024 and test on 2025 (split by the year column: the future must not leak into the past). Build a pipeline that one-hot encodes product_id and store, scales ["price", "discount_pct", "promo", "holiday_week", "avg_high_temp_f"], and ends with Ridge(). Report the test mean absolute error. Then wrap the same pipeline in TransformedTargetRegressor(regressor=..., func=np.log1p, inverse_func=np.expm1), which fits on log units sold and converts predictions back, and compare. Include the "predict the training mean" baseline.

💡 Hint

TransformedTargetRegressor is in sklearn.compose, Ridge in sklearn.linear_model, DummyRegressor in sklearn.dummy, and mean_absolute_error in sklearn.metrics. Units sold is heavily right-skewed, which is why a log target might help.

✅ Solution 
from sklearn.compose import TransformedTargetRegressor
from sklearn.dummy import DummyRegressor
from sklearn.linear_model import Ridge
from sklearn.metrics import mean_absolute_error

demand = pd.read_csv("data/weekly_demand.csv")
d_numeric = ["price", "discount_pct", "promo", "holiday_week", "avg_high_temp_f"]
d_cats = ["product_id", "store"]
d_train, d_test = demand[demand["year"] == 2024], demand[demand["year"] == 2025]

demand_pipe = Pipeline([
    ("prep", ColumnTransformer([
        ("scale", StandardScaler(), d_numeric),
        ("onehot", OneHotEncoder(handle_unknown="ignore"), d_cats),
    ])),
    ("model", Ridge()),
])
log_target = TransformedTargetRegressor(regressor=demand_pipe, func=np.log1p, inverse_func=np.expm1)

for name, reg in [("mean baseline", DummyRegressor()), ("ridge", demand_pipe), ("ridge, log target", log_target)]:
    reg.fit(d_train[d_numeric + d_cats], d_train["units_sold"])
    mae = mean_absolute_error(d_test["units_sold"], reg.predict(d_test[d_numeric + d_cats]))
    print(f"{name:18s} test MAE {mae:6.2f} units")

Output

mean baseline      test MAE  17.13 units
ridge              test MAE  11.28 units
ridge, log target  test MAE  10.70 units

Both pipelines beat the baseline by a wide margin, and the log target helps further: on the log scale, a product's price and season effects act as percentages, which suits products that sell 5 units and products that sell 200 alike. The whole thing, target transform included, is still one estimator you could cross-validate or save. Lessons 2.3 and 3.1 improve this demand model.

🏋️ Exercise 4: A Grid That Swaps Models (Stretch)

A GridSearchCV grid can be a list of dictionaries, and a parameter value can be a whole estimator. Build one grid search that compares logistic regression with C in [0.1, 1.0] against HistGradientBoostingClassifier(random_state=42) with learning_rate in [0.05, 0.1], all behind the same preprocessing. Print the best parameters and score, then print every candidate's mean score from cv_results_.

💡 Hint

Each dictionary sets "model": [SomeEstimator()] plus that estimator's own "model__..." settings. pd.DataFrame(grid.cv_results_) has the columns params and mean_test_score.

✅ Solution 
from sklearn.model_selection import GridSearchCV

grid = GridSearchCV(
    churn_pipeline(LogisticRegression()),
    param_grid=[
        {"model": [LogisticRegression()], "model__C": [0.1, 1.0]},
        {"model": [HistGradientBoostingClassifier(random_state=42)], "model__learning_rate": [0.05, 0.1]},
    ],
    cv=cv, scoring="roc_auc",
)
grid.fit(X_train, y_train)
print(f"best: {type(grid.best_params_['model']).__name__} {grid.best_score_:.3f}")

results = pd.DataFrame(grid.cv_results_)
for params, score in zip(results["params"], results["mean_test_score"]):
    setting = {k: v for k, v in params.items() if k != "model"}
    print(f"{type(params['model']).__name__:31s} {setting}  {score:.3f}")

❓ Common Questions at This Stage

Pipeline or make_pipeline: which should I use?

They build the same object. make_pipeline is shorter and names steps automatically after their classes, which is fine for small chains like a branch inside a ColumnTransformer. Pipeline with your own names is better for the top level, because model__C survives swapping the model for a different class, while logisticregression__C does not.

Is it a problem that preprocessing is refitted in every fold? It seems wasteful.

It is the point, not waste: each fold must imitate "a model trained without ever seeing these validation rows". For expensive steps, Pipeline(..., memory="cache_folder") caches fitted transformers so that a grid search does not refit identical preprocessing for every value of a model setting. On data of this size, you will not notice the cost.

Can a pipeline include steps that remove rows, such as dropping outliers or oversampling?

Not a scikit-learn Pipeline: its steps transform columns and must return the same rows. Removing or adding rows needs imblearn.pipeline.Pipeline from the imbalanced-learn package, which accepts samplers as steps and applies them during fit only. Lesson 2.5 uses it for oversampling, inside the folds for the same reasons as today.

How do I see the data exactly as the model sees it?

Slice off the model and transform: pipe[:-1].transform(X_test). Call pipe.set_output(transform="pandas") first (with sparse_output=False encoders) to get a DataFrame with readable column names, and pipe[:-1].get_feature_names_out() to list them. Module 7 uses these names to explain models.

📝 Lesson Summary

🎓 Key Takeaways

  • A Pipeline chains transformers and one final model into a single estimator with fit, predict, predict_proba and score
  • fit calls fit_transform on each step and fit on the last; predict calls only transform, then predict
  • Cross-validating or grid-searching the whole pipeline refits every learning step inside each fold, so validation rows cannot leak into training
  • Steps that learn from the target (target encoding, feature selection, resampling) leak the most when fitted outside the folds
  • step__parameter names reach any setting at any depth, for set_params and for grid searches; a whole step can be swapped by name
  • FunctionTransformer turns a plain function into a step; joblib.dump saves the whole fitted pipeline as one file (load only files you trust)
  • A pipeline separates rows, not columns: keeping leaky columns out of the feature list is still your job
