🧭 The Lab Notebook

Six months from now, someone at Pinecrest will ask: "The churn model in the retention dashboard: which data was it trained on, with which settings, and how good was it?" If the honest answer is "it was in a notebook on someone's laptop", the model cannot be trusted, fixed or improved. MLOps (machine-learning operations) is the set of habits and tools that keep models answerable after they leave the notebook. This lesson covers the first half: making results reproducible and keeping a record of every experiment. Lesson 12.2 covers serving and monitoring.

💡 Mental Model: The Lab Notebook

A good chemist writes down every experiment in a bound lab notebook: which batch of each chemical, which instrument, the temperature, the result, even the failures. Anyone can repeat the experiment from the notebook, and nobody argues about what was done. A machine-learning result has the same kinds of ingredients, and each one can quietly change the answer:

  • Code: the exact steps (version control, such as Git, takes care of this)
  • Data: the exact bytes of the file you trained on
  • Environment: Python and library versions
  • Randomness: seeds for splits, forests and anything shuffled
  • Settings: hyperparameters, features, split sizes

Record all five, plus the results, and you have a lab notebook for your models. MLflow is a lab notebook that fills itself in.

🤔 Why This Matters

Irreproducible results are not a rare accident; they are what happens by default. Two people rerun "the same" notebook and get different numbers because of an unseeded split, a refreshed data extract or an upgraded library, and an afternoon disappears into finding out why. The habits in this lesson take minutes to add and save days later. They also protect you: a model file is code-like, and the way you load it decides whether a stranger's file can run commands on your machine.

📂 The Model We Will Look After

The model is the churn pipeline from Module 2: impute, scale and one-hot encode inside a ColumnTransformer, then a classifier. A small function builds the pipeline around any classifier, so every experiment uses identical preprocessing.

import numpy as np
import pandas as pd
from sklearn.compose import ColumnTransformer
from sklearn.impute import SimpleImputer
from sklearn.model_selection import train_test_split
from sklearn.pipeline import Pipeline, make_pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

customers = pd.read_csv("data/customers_churn.csv")
numeric = ["tenure_months", "orders_12m", "spend_12m", "avg_order_value", "days_since_last_order", "returns_12m",
           "return_rate", "support_tickets_12m", "discount_share", "app_user", "email_opens_90d"]
categorical = ["home_store", "region", "age_group", "loyalty_tier", "preferred_category"]

X = customers[numeric + categorical]
y = customers["churned"]
X_train, X_test, y_train, y_test = train_test_split(X, y, test_size=0.25, stratify=y, random_state=42)

def build_pipeline(model):
    prep = ColumnTransformer([
        ("num", make_pipeline(SimpleImputer(strategy="median"), StandardScaler()), numeric),
        ("cat", make_pipeline(SimpleImputer(strategy="most_frequent"), OneHotEncoder(handle_unknown="ignore")), categorical),
    ])
    return Pipeline([("prep", prep), ("model", model)])

print(X_train.shape, X_test.shape)

Output

(4500, 16) (1500, 16)

Note what is already reproducible here: the split has a random_state, and preprocessing lives inside the pipeline, so it travels with the model when you save it. The cancellation_reason leak from Lesson 1.2 is, of course, not among the features.

🎲 Randomness, Data and Environment

Seeds

A random forest picks random rows and random features for every tree. Without a seed, each fit draws different random numbers, so the model and its scores change a little each time. Fit the same forest twice without a seed and twice with one:

from sklearn.ensemble import RandomForestClassifier
from sklearn.metrics import roc_auc_score

def forest_probabilities(seed):
    forest = build_pipeline(RandomForestClassifier(n_estimators=50, min_samples_leaf=5, random_state=seed))
    return forest.fit(X_train, y_train).predict_proba(X_test)[:, 1]

print("no seed:  two fits identical?", np.array_equal(forest_probabilities(None), forest_probabilities(None)))
print("seed 42:  two fits identical?", np.array_equal(forest_probabilities(42), forest_probabilities(42)))
for seed in [42, 7]:
    print(f"seed {seed:2d}: test AUC {roc_auc_score(y_test, forest_probabilities(seed)):.4f}")

Output

no seed:  two fits identical? False
seed 42:  two fits identical? True
seed 42: test AUC 0.8612
seed  7: test AUC 0.8560

With a seed, the same code gives the same model, bit for bit. A different seed gives a slightly different, equally valid model: the third decimal of the AUC moves. That tells you two things. Fix the seed so results are repeatable, and never treat a difference in the third decimal between two models as real unless it survives several seeds or cross-validation folds (Lesson 1.3).

⚠️ Seeds Are Necessary, Not Sufficient

A seed makes randomness repeatable on the same software. Change the number of threads, the operating system's math library or the scikit-learn version, and some results can differ in the last digits even with the same seed (this is why the deep-learning lessons label output "yours may vary slightly"). That is why the environment is one of the five ingredients.

Data: a Fingerprint, Not a File Name

"Trained on customers_churn.csv" is not enough: files with the same name get refreshed, edited and re-exported. A hash such as SHA-256 turns the exact bytes of a file into a 64-character fingerprint. Change a single character in the file and the fingerprint changes completely. Store the fingerprint with the model and you can later prove which data it saw.

import hashlib

def file_sha256(path):
    digest = hashlib.sha256()
    with open(path, "rb") as f:
        for chunk in iter(lambda: f.read(1_000_000), b""):   # read in 1 MB chunks: works for huge files too
            digest.update(chunk)
    return digest.hexdigest()

data_hash = file_sha256("data/customers_churn.csv")
print(len(data_hash), "hex characters, starting", data_hash[:16])

Output

64 hex characters, starting ac541c7e8691d33f

If your fingerprint starts with the same 16 characters, you have exactly the same file as this page. For data in a database rather than a file, record the query and the date of the extract, or hash an exported snapshot. Tools such as DVC take this further by versioning data files alongside Git.

Environment: Write Down the Versions

Record the versions of Python and the libraries that touch the model:

import platform
from importlib.metadata import version

environment = {"python": platform.python_version()}
for package in ["scikit-learn", "pandas", "numpy", "skops", "mlflow"]:
    environment[package] = version(package)
print(environment)

Output (yours may vary slightly)

{'python': '3.12.14', 'scikit-learn': '1.9.1', 'pandas': '3.0.6', 'numpy': '2.5.4', 'skops': '0.16.0', 'mlflow': '3.17.1'}

Your versions may differ from the page; what matters is that you record yours. For the whole environment, freeze every installed package into a lock file and keep it next to the code:

python -m pip freeze > requirements-lock.txt

The course's requirements.txt from Lesson 0.1 says which packages to install; the frozen lock file says exactly which versions you had, so the environment can be rebuilt later with python -m pip install -r requirements-lock.txt.

💾 Saving Models: joblib and Its Danger

Training takes time; predicting should not require retraining. Fit the pipeline once and save the fitted object to a file. The classic tool is joblib, which scikit-learn has recommended for years. Save the whole pipeline, not just the classifier at the end: the imputer medians, scaler means and one-hot categories are part of the model (Mistake 2 shows why).

import os
import joblib
from sklearn.ensemble import HistGradientBoostingClassifier

churn_model = build_pipeline(HistGradientBoostingClassifier(random_state=42)).fit(X_train, y_train)
test_auc = roc_auc_score(y_test, churn_model.predict_proba(X_test)[:, 1])
print(f"test AUC: {test_auc:.4f}")

joblib.dump(churn_model, "churn_model.joblib")
reloaded = joblib.load("churn_model.joblib")
print("same predictions after reload:", np.array_equal(reloaded.predict_proba(X_test), churn_model.predict_proba(X_test)))
print(f"file size: {os.path.getsize('churn_model.joblib') / 1e6:.2f} MB")

Output

test AUC: 0.8598
same predictions after reload: True
file size: 0.38 MB

It works, and the reloaded model gives identical predictions. Now the catch. joblib files are Python pickles, and a pickle is not just data: it is a small program of instructions for rebuilding objects, and one allowed instruction is "call this function with these arguments". Here is a harmless demonstration: an object whose saved form tells Python to call print while it is being loaded.

import pickle

class NotReallyAModel:
    def __reduce__(self):                       # tells pickle how to "rebuild" this object
        return (print, ("This line ran while the file was being LOADED.",))

with open("innocent_looking_model.pkl", "wb") as f:
    pickle.dump(NotReallyAModel(), f)

loaded = joblib.load("innocent_looking_model.pkl")
print("what came back:", loaded)

Output

This line ran while the file was being LOADED.
what came back: None

🛑 Loading a Pickle Runs Code

Nothing was "predicted"; just opening the file ran a function. Here it was print. In a malicious file it could be any function in Python: one that deletes files, installs software or sends your data away, with your permissions. Never load a .pkl or .joblib file you did not create yourself or receive from a source you fully trust. That includes models downloaded from the internet and files attached to messages. Treat a model file like a program you are about to run.

One more practical problem: a pickle stores references to scikit-learn's internal classes. Load it with a different scikit-learn version and you get an InconsistentVersionWarning, and the model may behave differently or fail. That is another reason to record the environment next to every saved model.

🔐 Safer Saving with skops

skops.io saves scikit-learn models in a format that describes the objects instead of storing instructions to run. When loading, it only rebuilds types on its list of known, safe types. Anything else must be named by you, explicitly, before it will load.

import skops.io as sio

sio.dump(churn_model, "churn_model.skops")
unknown_types = sio.get_untrusted_types(file="churn_model.skops")
print(unknown_types)

Output

['numpy.dtype', 'sklearn.ensemble._hist_gradient_boosting.predictor.TreePredictor']

get_untrusted_types reads the file without loading it and lists the types that are not on skops's default safe list. Here there are two: a NumPy data type and the tree structure used by histogram gradient boosting. You created this file a moment ago, so you can review the list and trust exactly these two. Write the list out in your code rather than passing whatever the file reports: if a future file asks for something new, you want the load to stop and make you look.

trusted_types = ["numpy.dtype", "sklearn.ensemble._hist_gradient_boosting.predictor.TreePredictor"]

safe_model = sio.load("churn_model.skops", trusted=trusted_types)
print(type(safe_model).__name__, [name for name, _ in safe_model.steps])
print("same predictions:", np.array_equal(safe_model.predict_proba(X_test), churn_model.predict_proba(X_test)))

Output

Pipeline ['prep', 'model']
same predictions: True

⚠️ Safer, Not Magic

skops blocks the "run any function" attack that makes pickle dangerous, but trusting a type is still a decision. Its own error message (Mistake 1) explains that a deliberately malformed gradient-boosting tree could crash the process at prediction time. The rule stays the same: only load models from sources you trust, and use skops so that the format itself cannot run code on load.

📝 A Model Card Next to the File

A model file without its story is half a lab notebook. Write a small JSON model card beside it with everything a future reader needs: what it is, what it saw, how good it was, and how to load it.

import json

model_card = {
    "model_file": "churn_model.skops",
    "estimator": type(churn_model[-1]).__name__,
    "features": numeric + categorical,
    "data_file": "data/customers_churn.csv",
    "data_sha256": data_hash,
    "split": {"test_size": 0.25, "stratify": "churned", "random_state": 42},
    "train_rows": len(X_train),
    "test_auc": round(test_auc, 4),
    "environment": environment,
    "skops_trusted_types": trusted_types,
}
with open("churn_model.json", "w") as f:
    json.dump(model_card, f, indent=2)

print(json.dumps({key: model_card[key] for key in ["estimator", "train_rows", "test_auc"]}, indent=2))

Output

{
  "estimator": "HistGradientBoostingClassifier",
  "train_rows": 4500,
  "test_auc": 0.8598
}

Professional model cards also describe the intended use, known limitations and fairness checks (Lesson 7.3). For a churn model, "intended for ranking customers for retention offers, not for decisions about individual accounts" is exactly the kind of sentence that belongs there.

📒 Experiment Tracking with MLflow

Hand-written cards are fine for one model. During a project you try dozens of variations, and you will not remember which settings gave which score. MLflow is an open-source tool that records every run (one training attempt) with its parameters, metrics, files and model, grouped into experiments, and gives you a web page to compare them.

graph TD A["Tracking store: mlflow.db"] --> B["Experiment: churn-lesson"] B --> C["Runs: logreg, hgb, final-hgb"] C --> D["Params and metrics"] C --> E["Tags and artifacts"]

MLflow stores everything locally by default; no server or account is needed. Point it at a SQLite database file in your project folder and name an experiment:

import mlflow

mlflow.set_tracking_uri("sqlite:///mlflow.db")     # a single local database file in this folder
mlflow.set_experiment("churn-lesson")
print(mlflow.get_tracking_uri())

Output

sqlite:///mlflow.db

The first time, MLflow creates mlflow.db and prints a few INFO lines while it sets up its tables (in a notebook they appear in a pink or gray box under the cell); that is normal. Older tutorials use a folder called mlruns instead; Mistake 3 shows what current MLflow says about that.

Logging Runs

Each with mlflow.start_run(...) block is one run. Inside it, log the settings with log_params, the results with log_metrics, and anything else useful as a tag. Logging model.get_params() records every hyperparameter, including the defaults you never typed, which are exactly the ones you forget.

from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import StratifiedKFold, cross_val_score

cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=42)
candidates = {
    "logreg": LogisticRegression(max_iter=1000),
    "hgb": HistGradientBoostingClassifier(random_state=42),
}

for name, model in candidates.items():
    with mlflow.start_run(run_name=name):
        scores = cross_val_score(build_pipeline(model), X_train, y_train, cv=cv, scoring="roc_auc")
        mlflow.log_params(model.get_params())
        mlflow.set_tags({"estimator": type(model).__name__, "data_sha256": data_hash})
        mlflow.log_metrics({"cv_auc": scores.mean(), "cv_auc_std": scores.std()})
        print(f"{name:7s} CV AUC {scores.mean():.3f} ± {scores.std():.3f}")

Output

logreg  CV AUC 0.832 ± 0.023
hgb     CV AUC 0.861 ± 0.013

The tracking store now holds both runs. Query them like a table: search_runs returns a pandas DataFrame with one row per run and columns named params.*, metrics.* and tags.*.

runs = mlflow.search_runs(experiment_names=["churn-lesson"], order_by=["metrics.cv_auc DESC"])
print(runs[["tags.mlflow.runName", "tags.estimator", "metrics.cv_auc", "params.max_iter"]].round(4).to_string(index=False))

Output

tags.mlflow.runName                 tags.estimator  metrics.cv_auc params.max_iter
                hgb HistGradientBoostingClassifier          0.8615             100
             logreg             LogisticRegression          0.8324            1000

Parameters are stored as text (params.max_iter is "1000" for one model and "100" for the other), metrics as numbers. Sorting by metrics.cv_auc puts gradient boosting first, as in Module 5.

Logging the Model Itself

A run can also store the fitted model as an artifact. mlflow.sklearn.log_model saves the pipeline (in the skops format by default for scikit-learn models, so the trusted-types list comes along), plus a description of the input columns and the package requirements. Log the final model with its test score and the model card:

requirements = [f"scikit-learn=={version('scikit-learn')}", f"skops=={version('skops')}"]

with mlflow.start_run(run_name="final-hgb") as run:
    mlflow.log_params(churn_model[-1].get_params())
    mlflow.log_metric("test_auc", test_auc)
    mlflow.set_tag("data_sha256", data_hash)
    logged = mlflow.sklearn.log_model(
        churn_model, name="model", input_example=X_train.head(3),
        pip_requirements=requirements, skops_trusted_types=trusted_types,
    )
    mlflow.log_artifact("churn_model.json")

print("run id:   ", run.info.run_id)
print("model uri:", logged.model_uri)

Output (your numbers will differ)

run id:    a6cbe1778f25416490cbf14f5c3b1799
model uri: models:/m-f62ff692c869475588fb8453e198f639

Run IDs and model IDs are random, so yours differ from the page. Passing pip_requirements pins the exact versions to install when someone reuses the model; without it, MLflow tries to work them out itself, which is slower and may record more packages than you need. Anyone with access to the tracking store can now load this exact model by its URI:

from_mlflow = mlflow.sklearn.load_model(logged.model_uri)
print(type(from_mlflow).__name__)
print("same predictions:", np.array_equal(from_mlflow.predict_proba(X_test), churn_model.predict_proba(X_test)))

Output

Pipeline
same predictions: True

The MLflow Web Page

Everything above is also browsable. In a terminal, in your project folder (with the environment active), start the MLflow user interface:

mlflow ui --backend-store-uri sqlite:///mlflow.db

Open http://127.0.0.1:5000 in your browser. You will see the churn-lesson experiment with its three runs; tick runs to compare their parameters and metrics side by side, and open final-hgb to find the model and churn_model.json under its artifacts. Press Ctrl+C in the terminal to stop the server.

✅ What You Have Now

Seeds for randomness, a fingerprint for data, versions for the environment, logged parameters for settings, and the code in your notebook or script (in Git). All five ingredients are recorded, and the model can be reloaded safely and checked. That is reproducibility.

⚠️ Common Mistakes

1. Loading a skops File Without Reviewing Its Types

from skops.io.exceptions import UntrustedTypesFoundException

sio.load("churn_model.skops")

Error

UntrustedTypesFoundException: Untrusted types found in the file: ['numpy.dtype', 'sklearn.ensemble._hist_gradient_boosting.predictor.TreePredictor'].

- sklearn.ensemble._hist_gradient_boosting.predictor.TreePredictor: sklearn.ensemble._hist_gradient_boosting.predictor.TreePredictor (used by HistGradientBoosting* models) stores raw node indices (left, right, feature_idx) in its nodes array that scikit-learn indexes into without bounds checking. A malicious file can set these to out-of-range values: skops loads the object successfully, but calling .predict() on it can then crash the process (segfault) or read out-of-bounds memory. If you created the file yourself or otherwise fully trust its source, you can load it with trusted=["sklearn.ensemble._hist_gradient_boosting.predictor.TreePredictor"].

Only add the specific types you have reviewed and trust to the `trusted` argument; avoid passing everything reported by get_untrusted_types() just to make a file load.

What it means: the file contains types outside skops's safe list, and skops refuses to guess whether you trust them. The message even explains the specific risk of each type. Fix: call get_untrusted_types, review the list, and pass the types you accept explicitly with trusted=[...]. Do not paste trusted=sio.get_untrusted_types(...) as a habit: that trusts whatever any file asks for, which defeats the point.

2. Saving the Classifier but Not the Pipeline

joblib.dump(churn_model[-1], "classifier_only.joblib")     # just the last step
joblib.load("classifier_only.joblib").predict(X_test)

Error

ValueError: could not convert string to float: 'Asheville'

What it means: the classifier on its own expects the preprocessed numbers, not raw columns like home_store. Without the fitted imputers, scaler and encoder, the model cannot be used, and you cannot rebuild them exactly without the original training data. If the raw data happens to be all numeric, it is worse: no error, just wrong predictions from unscaled inputs. Fix: save the whole fitted Pipeline; it is one object.

3. Following an Old Tutorial's mlruns Folder

from mlflow.exceptions import MlflowException

mlflow.set_tracking_uri("./mlruns")
mlflow.set_experiment("churn-lesson")

Error

MlflowException: The filesystem tracking backend (e.g., './mlruns') is in maintenance mode and will not receive further updates. Please migrate to a database backend (e.g., 'sqlite:///mlflow.db') to access the latest MLflow features. The `mlflow migrate-filestore` tool migrates your existing data losslessly. See https://mlflow.org/docs/latest/self-hosting/migrate-from-file-store for migration guidance. If the filesystem backend is required for your workflow, set `MLFLOW_ALLOW_FILE_STORE=true` to opt out of this exception.

What it means: older MLflow versions stored runs as plain files in an mlruns folder, and many tutorials still show that. Current MLflow refuses the file store by default and points you to a database backend. Fix: use mlflow.set_tracking_uri("sqlite:///mlflow.db") as this lesson does. If you have an old mlruns folder, the message names the mlflow migrate-filestore tool that converts it.

4. Changing a Parameter Inside a Run

mlflow.set_tracking_uri("sqlite:///mlflow.db")      # back to the working store after Mistake 3
mlflow.set_experiment("churn-lesson")

with mlflow.start_run(run_name="oops"):
    mlflow.log_param("learning_rate", 0.1)
    mlflow.log_param("learning_rate", 0.05)          # "let me just try another value"

Error (your run ID will differ)

MlflowException: Changing param values is not allowed. Param with key='learning_rate' was already logged with value='0.1' for run ID='876877b11e4740a9bf8f07779439b94b'. Attempted logging new value '0.05'.

The cause of this error is typically due to repeated calls
to an individual run_id event logging.
...

What it means: a run is a record of one experiment, and MLflow will not let its settings be rewritten afterwards. That is a feature: a logged parameter can be trusted. Fix: one run per setting. Loop over the values and start a new run for each, as the project does. The failed run stays in the store, marked as failed; you can delete it in the web page.

🛠️ Project: A Tracked, Reproducible Churn Model

Put every habit together. You will compare four candidate models with cross-validation, track each in MLflow, pick the best from the tracking store, score it once on the test set, save it with skops beside a model card, and finally prove that a fresh session can rebuild the exact result from the files alone. Work in a new notebook called lesson_12_1_project, or a script called tracked_churn.py. Allow about 50 minutes.

🛠️ Step 1: One configuration, one fingerprint (5 min)

Put every setting in one dictionary at the top. Changing an experiment then means changing one line, and the dictionary itself can be logged.

import hashlib
import json
import numpy as np
import pandas as pd
import mlflow
import skops.io as sio
from importlib.metadata import version

CONFIG = {
    "data_file": "data/customers_churn.csv",
    "numeric": ["tenure_months", "orders_12m", "spend_12m", "avg_order_value", "days_since_last_order",
                "returns_12m", "return_rate", "support_tickets_12m", "discount_share", "app_user", "email_opens_90d"],
    "categorical": ["home_store", "region", "age_group", "loyalty_tier", "preferred_category"],
    "target": "churned",
    "test_size": 0.25,
    "seed": 42,
    "cv_folds": 5,
    "experiment": "churn-project",
}

def file_sha256(path):
    digest = hashlib.sha256()
    with open(path, "rb") as f:
        for chunk in iter(lambda: f.read(1_000_000), b""):
            digest.update(chunk)
    return digest.hexdigest()

data_hash = file_sha256(CONFIG["data_file"])
print("data fingerprint:", data_hash[:16])

Output

data fingerprint: ac541c7e8691d33f

🛠️ Step 2: Data, split and candidates (10 min)

Everything reads from CONFIG. The candidates are the models from Module 5, each with its seed.

from sklearn.compose import ColumnTransformer
from sklearn.ensemble import HistGradientBoostingClassifier, RandomForestClassifier
from sklearn.impute import SimpleImputer
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import StratifiedKFold, cross_val_score, train_test_split
from sklearn.pipeline import Pipeline, make_pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

customers = pd.read_csv(CONFIG["data_file"])
X = customers[CONFIG["numeric"] + CONFIG["categorical"]]
y = customers[CONFIG["target"]]
X_train, X_test, y_train, y_test = train_test_split(
    X, y, test_size=CONFIG["test_size"], stratify=y, random_state=CONFIG["seed"])

def build_pipeline(model):
    prep = ColumnTransformer([
        ("num", make_pipeline(SimpleImputer(strategy="median"), StandardScaler()), CONFIG["numeric"]),
        ("cat", make_pipeline(SimpleImputer(strategy="most_frequent"), OneHotEncoder(handle_unknown="ignore")),
         CONFIG["categorical"]),
    ])
    return Pipeline([("prep", prep), ("model", model)])

seed = CONFIG["seed"]
candidates = {

    "forest": RandomForestClassifier(n_estimators=200, min_samples_leaf=5, n_jobs=-1, random_state=seed),
    "hgb": HistGradientBoostingClassifier(random_state=seed),

}

🛠️ Step 3: Track every candidate (15 min)

One run per candidate, each with its full parameters, the configuration, the data fingerprint and the cross-validated AUC. The test set is not used here.

mlflow.set_tracking_uri("sqlite:///mlflow.db")
mlflow.set_experiment(CONFIG["experiment"])
cv = StratifiedKFold(n_splits=CONFIG["cv_folds"], shuffle=True, random_state=seed)

for name, model in candidates.items():
    with mlflow.start_run(run_name=name):
        scores = cross_val_score(build_pipeline(model), X_train, y_train, cv=cv, scoring="roc_auc")
        mlflow.log_params(model.get_params())
        mlflow.log_dict(CONFIG, "config.json")
        mlflow.set_tags({"estimator": type(model).__name__, "data_sha256": data_hash})
        mlflow.log_metrics({"cv_auc": scores.mean(), "cv_auc_std": scores.std()})
        print(f"{name:8s} CV AUC {scores.mean():.4f} ± {scores.std():.4f}")

Choose the winner by querying MLflow, not by scrolling up: in a real project the runs may come from different days or people. Then refit it on the full training set and score the test set exactly once.

💡 Hint

✅ Solution 
"""Train the Pinecrest churn model reproducibly: python train_churn.py"""
import hashlib
import json

import pandas as pd
import skops.io as sio
from sklearn.compose import ColumnTransformer
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.impute import SimpleImputer
from sklearn.metrics import roc_auc_score
from sklearn.model_selection import train_test_split
from sklearn.pipeline import Pipeline, make_pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

CONFIG = {
    "data_file": "data/customers_churn.csv",
    "numeric": ["tenure_months", "orders_12m", "spend_12m", "avg_order_value", "days_since_last_order",
                "returns_12m", "return_rate", "support_tickets_12m", "discount_share", "app_user", "email_opens_90d"],
    "categorical": ["home_store", "region", "age_group", "loyalty_tier", "preferred_category"],
    "target": "churned",
    "test_size": 0.25,
    "seed": 42,
}


def file_sha256(path):
    digest = hashlib.sha256()
    with open(path, "rb") as f:
        for chunk in iter(lambda: f.read(1_000_000), b""):
            digest.update(chunk)
    return digest.hexdigest()


def main():
    data = pd.read_csv(CONFIG["data_file"])
    X = data[CONFIG["numeric"] + CONFIG["categorical"]]
    y = data[CONFIG["target"]]
    X_train, X_test, y_train, y_test = train_test_split(
        X, y, test_size=CONFIG["test_size"], stratify=y, random_state=CONFIG["seed"])

    prep = ColumnTransformer([
        ("num", make_pipeline(SimpleImputer(strategy="median"), StandardScaler()), CONFIG["numeric"]),
        ("cat", make_pipeline(SimpleImputer(strategy="most_frequent"), OneHotEncoder(handle_unknown="ignore")),
         CONFIG["categorical"]),
    ])
    model = Pipeline([("prep", prep), ("model", HistGradientBoostingClassifier(random_state=CONFIG["seed"]))])
    model.fit(X_train, y_train)
    auc = roc_auc_score(y_test, model.predict_proba(X_test)[:, 1])

    sio.dump(model, "churn_script.skops")
    card = {"data_sha256": file_sha256(CONFIG["data_file"]), "test_auc": round(auc, 4), "config": CONFIG}
    with open("churn_script.json", "w") as f:
        json.dump(card, f, indent=2)
    print(f"data {card['data_sha256'][:16]}  test AUC {auc:.4f}  saved churn_script.skops")


if __name__ == "__main__":
    main()

Output

data ac541c7e8691d33f  test AUC 0.8598  saved churn_script.skops

Every run prints the same line, because every ingredient is pinned: the data (checked by fingerprint), the seed, the settings and, as long as you keep the same environment, the library versions. The if __name__ == "__main__": guard lets other code import file_sha256 from this file without training a model. A natural next step is adding the MLflow logging from the project to the script.

❓ Common Questions at This Stage

What about mlflow.sklearn.autolog()?

Autologging patches scikit-learn so that every fit logs its parameters, some training metrics and the model automatically. It is a great way to start, and a fast way to fill the tracking store with runs you did not mean to keep. This lesson logs explicitly so you see what a run contains and log the metric that matters (cross-validated AUC), which autolog cannot guess. Try autolog once in the bonus challenge and compare what it records.

Should I use joblib or skops?

For files you create and load yourself, in the same environment, joblib is convenient and common. For anything that crosses a trust boundary (shared with a team, downloaded, uploaded to a model hub, loaded by a server) prefer skops, and keep an explicit trusted-types list. MLflow already uses skops by default for scikit-learn models. For PyTorch, the equivalent habit is saving state_dict and loading with torch.load(..., weights_only=True) (Lesson 10.2).

Where should mlflow.db live, and should it go in Git?

Keep it in the project folder for personal work, and add mlflow.db and the mlruns artifact folder to .gitignore: they hold binary files and grow quickly. A team runs one shared MLflow server with a proper database and artifact storage, and everybody sets their tracking URI to it. The code you wrote today works unchanged; only the URI differs.

MLflow printed many INFO and WARNING lines. Did something go wrong?

Usually not. The first run creates database tables (INFO lines), and logging a model may warn that it could not determine your pip version or that an integer column cannot hold missing values. Read them once; they are notes, not errors. A red traceback that ends in an exception is an error.

Is this overkill for a learning project?

A seed, a fingerprint and a short JSON card take five minutes and make your portfolio projects far more convincing: anyone can rerun them and get your numbers. MLflow pays off as soon as you have more than a handful of experiments, which in the capstone you will.

📝 Lesson Summary

🎓 Key Takeaways

  • A result is reproducible when code, data, environment, randomness and settings are all recorded
  • Seeds make randomness repeatable on the same software; differences in the third decimal between seeds are noise
  • A SHA-256 fingerprint proves which exact data file a model saw; pip freeze records the environment
  • Save the whole fitted pipeline; joblib works but is a pickle, and loading a pickle can run arbitrary code
  • skops.io refuses unknown types until you review them and pass an explicit trusted= list
  • MLflow records runs (params, metrics, tags, artifacts, models) in a local SQLite store and lets you query and reload them
  • A model card (JSON beside the model) holds what a future reader needs, including intended use
